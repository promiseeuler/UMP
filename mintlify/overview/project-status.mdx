UMP 0.1 is an alpha reference implementation and software qualification laboratory. It provides a complete, bounded semantic protocol for shared robot awareness and high-level collaboration, but it does not claim universal hardware compatibility or production safety certification. This page documents exactly what the current release delivers and what remains outside its scope.

## What is implemented

The UMP 0.1 reference implementation includes:

- **Canonical protocol envelopes** — UTF-8 JSON encoding, lexical key order, size bounds, and schema validation for every message
- **Mutual-TLS transport** — TLS 1.3 with mandatory client certificates, certificate-to-envelope identity binding, and ALPN negotiation for `ump/0.1`
- **Identity binding** — one `urn:ump:robot:<robot-id>` URI per certificate, with peer fingerprint pinning and revocation checks
- **Disclosure controls** — per-peer outbound allowlists for message types and exact versioned capabilities
- **Replay protection** — durable sequence floors per source and session, persisted in SQLite WAL
- **Durable delivery** — FIFO outbox with bounded backpressure, exponential retry, and separate safety-stream priority
- **Credentials lifecycle** — staged enrollment, transactional activation, audit trail, and local revocation
- **Authority leases** — scoped, time-bounded, capability-specific grants stored and validated on the target robot
- **Reconciliation** — coordinator restart recovery with `assignment_query` and fingerprint-matched `assignment_snapshot`
- **Semantic robot registry** — manifest-first session acceptance, stale-state rejection, and capability-filtered peer views
- **Read-only inspector** — local SQLite-backed UI showing only recorded UMP traffic, with no injected demo data
- **Production observability** — optional content-free health, readiness, and Prometheus endpoints for long-running participant nodes
- **Protected remote inspection** — explicit TLS 1.3 and token-authenticated remote mode while loopback remains the default
- **Data recovery** — consistent SQLite backup, checksum and integrity verification, and overwrite-safe restore tooling
- **Deployment templates** — non-root production image plus hardened Compose and systemd examples
- **Software supply chain** — dependency, secret, and container scans with release checksums and a CycloneDX SBOM
- **Deterministic planner** — reference warehouse planner for integration tests; swappable with model-backed implementations
- **Standards mappings** — MassRobotics 1.0, VDA 5050 3.0, Open-RMF, ROS 2, and OPC UA Robotics 1.02 with conversion evidence
- **Mixed-fleet emulators** — mobile, inspection, and manipulator controller emulators for lab scenarios
- **Fault and load tests** — deterministic latency, jitter, loss, duplication, reordering, partition, and broker-restart profiles
- **Signed readiness reports** — Ed25519-signed evidence bundling runtime versions, scenario outcomes, delivery metrics, and artifact hashes
- **Gazebo warehouse scenario** — headless Gazebo Harmonic with ROS 2 Jazzy, running assignments through the native execution boundary

## What is not claimed

UMP 0.1 explicitly does not claim:

- Universal hardware compatibility with every robot manufacturer or model
- Production safety certification or functional-safety approval
- Manufacturer endorsement of any specific integration
- Replacement for native fleet management, autonomy, or safety systems
- Guaranteed timing performance, network resilience, or real-time determinism
- Certification that passing software tests qualifies arbitrary physical robots

<Tip>
  The correct milestone for UMP 0.1 is **ready for supervised hardware trials** after the readiness gate passes. This means the deterministic software path is verified, but physical compatibility, safety, and manufacturer-specific behavior must still be validated independently by the robot owner.
</Tip>

## Software release gates

Before calling a UMP revision production-ready as software, complete the unit,
conformance, package, container, security, staging recovery, rollback, and soak
checks for the exact immutable artifact being deployed. See the
[Software Release Gate](/validate/software-release) and
[Operations](/guides/operations) runbook.

## Hardware readiness gates

Before progressing from software verification to hardware trials, complete:

1. Full unit and integration test suite: `python3 -m unittest discover -s tests -v`
2. Protocol conformance: `ump-conformance conformance/v0.1`
3. Container transports, fault profiles, and load tests
4. Gazebo smoke test and eight-hour soak
5. Signed readiness report generation and verification

Learn more about the qualification process in [Hardware Readiness](/validate/hardware-readiness) and the trial progression in [Hardware Trials](/validate/hardware-trials).
