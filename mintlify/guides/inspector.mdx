The UMP inspector is a local, read-only operational view of observed protocol traffic. It displays robot manifests, current semantic state, advertised capabilities, and a correlated event timeline. The inspector never exposes raw manufacturer SDK data, sensor streams, or native controller internals. It also has no endpoint or UI action for assignments, cancellations, authority changes, or native commands.

A robot appears in the inspector only after a running UMP node has loaded a manufacturer adapter, published an authenticated manifest and semantic state, and recorded those messages in the exact inspector database being served. With no recorded messages, the UI deliberately shows zero robots, zero events, and "No UMP robots observed."

## What the inspector shows

For each genuinely observed robot, the inspector displays disclosed fields only:

- Stable robot identity, manufacturer, model, and robot class
- Operating mode, safety condition, operational health, and state freshness
- Battery level, charging status, observation time, and estimated runtime when supplied
- Current activity, intent, progress, assignment, resources, and blockers
- Advertised high-level capabilities
- Optional pose metadata and bounded sensor references
- Correlated manifests, states, assignments, cancellations, plans, and outcomes

Unknown, omitted, or unavailable native telemetry remains visibly unknown. The inspector does not estimate battery, health, task completion, or physical state.

## Start the inspector

<Steps>
  <Step title="Enable recording on a running node">
    Pass `--inspector-database` when starting `ump-node` or `ump-coordinator submit`:

    ```bash
    ump-node \
      --network /etc/ump/network.json \
      --adapter manufacturer_package.adapter:create_adapter \
      --assignment-database /var/lib/ump/assignments.sqlite3 \
      --authority-database /var/lib/ump/authority.sqlite3 \
      --credential-database /var/lib/ump/credentials.sqlite3 \
      --credential-directory /var/lib/ump/credentials \
      --inspector-database /var/lib/ump/inspector.sqlite3
    ```

    The path must be unique from every other runtime database role. Participant and coordinator preflight validate it without creating the file. The ready event reports `inspector_recording: true` when capture is active.
  </Step>
  <Step title="Serve the inspector UI">
    From an installed package:

    ```bash
    ump-inspector --database /var/lib/ump/inspector.sqlite3 --host 127.0.0.1 --port 8765
    ```

    From a source checkout:

    ```bash
    PYTHONPATH=src python3 -m ump.cli inspector \
      --database /var/lib/ump/inspector.sqlite3 --host 127.0.0.1 --port 8765
    ```

    Loopback access is the default. The server sends restrictive content
    security, cache, referrer, and content-type headers.
  </Step>
  <Step title="Open the UI">
    Navigate to `http://127.0.0.1:8765`. The UI polls the local snapshot endpoint and can run while another process appends to the database.
  </Step>
</Steps>

## Protected remote access

Remote binding fails closed unless you explicitly enable it and provide TLS 1.3
credentials plus a token containing at least 32 bytes:

```bash
ump-inspector \
  --database /var/lib/ump/inspector.sqlite3 \
  --host 0.0.0.0 --port 8765 --allow-remote \
  --auth-token-file /run/secrets/inspector-token \
  --tls-certificate /run/secrets/inspector-cert.pem \
  --tls-private-key /run/secrets/inspector-key.pem
```

Sign in with username `ump` and the exact token-file content as the password.
Keep this endpoint on a private management network. Deployments needing SSO,
per-user authorization, rate limits, or operator access logs must provide them
through a reviewed access proxy.

<Warning>
  Do not expose the inspector directly to the public internet. Inspector access
  is observational, but it can disclose robot identity and operational state.
</Warning>

<Note>
  The database passed to `ump-inspector` must be the same path supplied to the active `ump-node` or coordinator through `--inspector-database`. Serving a different compatible database is valid, but it will show only the traffic recorded in that database.
</Note>

## How recording works

The `InspectorRecorder` subscribes to all message types and writes canonical envelopes to an append-only SQLite WAL database managed by `InspectorStore`. Repeated message IDs and repeated source or session sequence values are ignored.

Recorder write failures are latched instead of propagating through the message handler that already processed an inbound envelope. Supported owner services include that latch in recurring runtime health checks and fail visibly after a recording fault.

For embedded runtimes, attach one recorder to the same `MessageBus`:

```python
from ump.inspector import InspectorRecorder, InspectorStore

store = InspectorStore("var/ump-inspector.sqlite3")
recorder = InspectorRecorder(bus, store)
```

## Operational limits

The inspector is observational, not a complete audit system. Recording must be
enabled to capture traffic, and database retention or export policy remains the
deployer's responsibility.

A `Live` indicator in the UI means the browser can reach the local inspector server. It does not by itself mean that any robot is connected. Use robot state freshness and network diagnostics to assess participant connectivity.

## Troubleshooting

<Accordion title="The UI shows zero robots">
  Confirm that the running node uses the exact same `--inspector-database` path. An empty UI means no compatible messages have been recorded. It does not prove that hardware, ROS, or a manufacturer SDK is disconnected elsewhere.
</Accordion>

<Accordion title="ump-inspector exits with status 2">
  The command requires an existing compatible recorder database and opens it with SQLite `mode=ro` and `query_only`. It validates the read-model columns before binding the HTTP listener. A missing, mistyped, unreadable, or incompatible path returns exit status `2`. The command does not create a parent directory, database, table, or protocol event.
</Accordion>
