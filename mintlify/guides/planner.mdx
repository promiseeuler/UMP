The UMP coordinator converts shared goals into validated, durable high-level assignments across multiple robots. It does not issue actuator commands, trajectories, or emergency stops. Instead, it matches goal steps to robot capabilities, checks authority leases and state freshness, and dispatches assignments only after every validation passes.

## Goal documents

Goals are JSON documents that describe a multi-robot task. A single goal uses the `ump-shared-goal-v1` schema. A batch of goals uses `ump-shared-goal-batch-v1` and can contain 1 to 256 goal objects.

Example single goal:

```json title="move-package.json"
{
  "goal_id": "goal-move-package-1",
  "description": "Move the sealed package from intake to storage shelf A",
  "participant_ids": [
    "robot-humanoid-1",
    "robot-quadruped-1",
    "robot-mobile-arm-1"
  ],
  "constraints": {"keep_upright": true},
  "deadline_ms": 1770000000000
}
```

Validate a goal before deployment:

```bash
ump-goal validate move-package.json
```

For batches:

```bash
ump-goal validate-batch shift-tasks.json
```

Goal documents reject unknown fields, duplicate participants, non-object constraints, invalid identifiers, and non-integer deadlines.

## Explore standard capabilities

Before writing goals, explore what capabilities are available in the UMP standard vocabulary:

```bash
ump-capability list
```

Show the full contract for a specific capability:

```bash
ump-capability show ump.material.carry/v1
```

Validate that a goal input conforms to a capability's input schema:

```bash
ump-capability validate-input ump.material.carry/v1 goal.json
```

## Coordinator commands

The coordinator CLI provides commands to preflight, submit, inspect, and manage goal runs.

### Preflight the coordinator

Validate deployment inputs before loading a planner or binding a listener:

```bash
ump-coordinator preflight \
  --network /etc/ump/coordinator-network.json \
  --credential-database /var/lib/ump/coordinator-credentials.sqlite3 \
  --credential-directory /var/lib/ump/coordinator-credentials \
  --database /var/lib/ump/coordinator.sqlite3
```

Preflight validates the network configuration, current active credential, certificate and key compatibility, owner-only private-key permissions, writable storage parents, and distinct database paths.

### Submit a goal

```bash
ump-coordinator submit \
  --network /etc/ump/coordinator-network.json \
  --credential-database /var/lib/ump/coordinator-credentials.sqlite3 \
  --credential-directory /var/lib/ump/coordinator-credentials \
  --database /var/lib/ump/coordinator.sqlite3 \
  --planner owner_planner:create_planner \
  --planner-config /etc/ump/planner.json \
  --goal /etc/ump/goals/move-package.json \
  --authority-lease robot-humanoid-1=owner-shift-a \
  --authority-lease robot-quadruped-1=owner-shift-b
```

The coordinator waits up to 30 seconds for a manifest and fresh semantic state from every participant before invoking the planner. It then waits up to five minutes for a terminal durable run result.

### Submit a batch

Replace `--goal` with `--goals` for batch submission:

```bash
ump-coordinator submit \
  ... \
  --goals /etc/ump/goals/shift-tasks.json \
  --authority-lease robot-humanoid-1=owner-shift-a
```

Goal IDs must be unique. The coordinator validates every proposed plan before journaling or publishing any run. Runs progress independently under one bounded completion deadline. Exit status is successful only when every run succeeds.

### Inspect and list runs

Check the status of a specific plan:

```bash
ump-coordinator status \
  --database /var/lib/ump/coordinator.sqlite3 \
  --plan-id PLAN_ID
```

List recent runs newest first, optionally filtered by status:

```bash
ump-coordinator runs \
  --database /var/lib/ump/coordinator.sqlite3 \
  --status active \
  --limit 100
```

Show detailed information about a specific run:

```bash
ump-coordinator show \
  --database /var/lib/ump/coordinator.sqlite3 \
  --plan-id PLAN_ID
```

## Plan validation

Every returned plan is untrusted. Before publishing assignments, the coordinator validates:

- Message size and goal identity
- Participants against network disclosure policy
- Fresh state from every participant
- Capability availability and matching
- Deadline feasibility
- Dependency chains for cycles
- Authority leases for scope and validity

Each robot then independently validates its local lease, capability input schema, resource availability, and safety policy. A planner cannot bypass those checks.

## Dependency chains

Plan steps can declare required predecessor steps. Only `succeeded` satisfies a dependency. A failed, rejected, or unknown step blocks its dependent steps. Independent pending steps remain representable but are not dispatched after a run enters a terminal failed or unknown state.

## Planner contract

Implement `ump.Planner` to create custom planners:

```python
from pathlib import Path
from ump import Plan, Planner, RobotManifest, RobotState, SharedGoal

class SitePlanner:
    planner_id = "example.site/planner/v1"

    def propose(
        self,
        goal: SharedGoal,
        manifests: dict[str, RobotManifest],
        states: dict[str, RobotState],
    ) -> Plan:
        ...

def create_planner(config_path: Path | None) -> Planner:
    return SitePlanner()
```

Load the planner factory explicitly:

```python
from ump import load_planner

planner = load_planner("site_planner:create_planner", "planner.json")
```

The deterministic reference factory `ump.demo:create_warehouse_planner` is available for integration tests and examples.
